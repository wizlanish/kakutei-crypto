# kakutei-crypto 設計書

日付: 2026-10-14
状態: 承認済み（ユーザーから「すべて任せる」の指示）

## 1. 目的

日本居住の個人が、国内暗号資産交換業者の取引履歴から**暗号資産の雑所得**を計算できるローカルツール。

- **Claude が「読む」、コードが「計算する」**：交換業者ごとにバラバラな CSV / PDF を、Claude Code が統一台帳に変換する。所得計算はテスト済みの決定的なコードだけが行い、LLM は一切計算しない。
- **完全ローカル**：取引履歴は外部サーバーに送らない（Claude Code の利用を除く）。
- **検証可能**：国税庁 FAQ の計算例をゴールデンテストにし、全取引について「なぜこの金額か」を明細で出力する。

成功基準:
1. 国税庁 FAQ 2-4（総平均法 3,106,000 円 / 移動平均法 3,080,200 円）と 2-8（所得 2,189,000 円）をテストで再現する。
2. OKJ（注文履歴・入出金口座履歴）と Coincheck（様式1）の実ファイル形式を読み込める。
3. 合成データ（架空ユーザーの 1 年分、3 交換業者）で import → check → calc → xlsx が一気通貫で動く。
4. README を 30 秒読めば、何をするツールで、なぜ信頼できるかが分かる。

## 2. スコープ

対象（v1）:
- 現物の円建て売買、暗号資産同士の交換、暗号資産で払った手数料
- 自分の口座間の送付（所得は生じない）
- ステーキング・レンディング等の報酬（受取時の時価を収入計上）
- 分裂（分岐）による取得（取得価額 0 円、FAQ 1-6）
- 総平均法（個人の法定評価方法）と移動平均法
- 年をまたぐ繰越（年末評価額を翌年の年始残高へ）

対象外（README の Roadmap に記載）: 証拠金・CFD・信用取引、DeFi・NFT、海外交換業者・外貨換算、法人、Web UI、価格の自動取得。

## 3. 税務ルール（根拠: 国税庁「暗号資産等に関する税務上の取扱いについて（FAQ）」令和7年12月改訂）

| 取引 | 扱い | 根拠 |
|---|---|---|
| 円で購入 | 取得。取得価額 = 支払額 + 購入手数料 | FAQ 1-5 |
| 円で売却 | 譲渡。収入 = 売却額、売却手数料は必要経費 | FAQ 1-1, 2-3 |
| 暗号資産 A→B の交換 | A を時価で譲渡、B を同じ時価で取得 | FAQ 1-3 |
| 暗号資産で決済・送付手数料 | A を譲渡（下記の簡便処理） | FAQ 1-2 |
| 報酬（ステーキング等） | 受取時の時価を収入計上し、同額で取得 | FAQ 1-7, 2-9 |
| 分裂（分岐） | 取得価額 0 円、取得時に所得なし | FAQ 1-6 |
| 自分の口座間の送付 | 所得なし（同一銘柄は全交換業者で合算して計算） | FAQ 2-8 |

**総平均法**（銘柄ごと・年ごと、FAQ 2-4 と計算書の欄記号に合わせる）:
- A/B = 年初数量/金額（前年の H/I）、C/D = 年中取得数量/金額
- E = (B + D) / (A + C)（総平均単価）
- H = 年末数量、I = E × H（年末評価額）、G = B + D − I（売却原価）

**移動平均法**: 取得のたびに平均単価 = 簿価総額 / 保有数量を見直す。譲渡時は直前の平均単価 × 数量を原価とする。

**暗号資産で払った手数料の簡便処理**: 時価で譲渡して同額を必要経費にする処理と、収入 0 円で譲渡（原価だけが売却原価に入る）処理は、**所得金額が一致する**。v1 は時価が不要な後者を採用し、README に明記する。

**端数**: 計算は Decimal で行い、円未満は表示する時点で切り捨てる。I は円未満切り捨てとし、G = B + D − I で恒等式を保つ（総平均法）。

## 4. アーキテクチャ

```
原始ファイル (CSV/PDF) ──► 取込み
   ├ 既知形式: 決定的パーサー (parsers/)
   └ 未知形式・PDF: Claude Code スキルが統一台帳の行を作成（出典行つき）→ ユーザー確認
                ▼
        統一台帳 ledger.csv（様式1 準拠：増加通貨/数量・減少通貨/数量・手数料）
                ▼
        check: 時価の欠落、保有数量がマイナスになる箇所、未分類の取引
                ▼
        engine: 総平均法 / 移動平均法（Decimal、年ごと、繰越あり）
                ▼
        report: 端末サマリー + xlsx（計算書シート + 全取引の明細シート）
```

### 4.1 統一台帳（`ledger.csv`）

Coincheck の「様式1」に倣い、すべての取引を「何が増え、何が減ったか」で表す。

| 列 | 意味 |
|---|---|
| `id` | 一意な ID（`<交換業者>-<元ID または行番号>`） |
| `timestamp` | ISO 8601、JST（`2026-03-16T15:37:34+09:00`） |
| `exchange` | `okj` / `coincheck` / `bitflyer` / … |
| `kind` | `buy` `sell` `swap` `reward` `fork` `transfer_in` `transfer_out` `opening` |
| `in_asset`, `in_qty` | 増加した資産と数量（正の数） |
| `out_asset`, `out_qty` | 減少した資産と数量（正の数） |
| `jpy_value` | 取引の円換算額（buy=支払額、sell=受取額、swap/reward=時価、opening=簿価） |
| `fee_asset`, `fee_qty` | 手数料の資産と数量（JPY の場合は円額） |
| `source` | 出典（`ファイル名#行番号`） |
| `note` | 補足（推定・要確認など） |

`JPY` は資産として記録するが、計算対象外。

### 4.2 取引種別ごとのエンジン処理

| kind | 処理 |
|---|---|
| `buy` | in を取得。取得価額 = jpy_value + 円手数料。手数料が in と同じ暗号資産なら、取得数量から差し引く |
| `sell` | out を譲渡。収入 = jpy_value。円手数料は必要経費 |
| `swap` | out を jpy_value で譲渡、in を jpy_value で取得（jpy_value 必須） |
| `reward` | 収入 += jpy_value、in を jpy_value で取得（jpy_value 必須） |
| `fork` | in を 0 円で取得 |
| `transfer_in` / `transfer_out` | 所得計算上は何もしない（自分の口座間） |
| `opening` | 計算開始時点の保有：in を jpy_value で取得扱い（最初の年の年初残高） |
| 暗号資産の手数料（全 kind 共通） | fee_qty を収入 0 円で譲渡 |

### 4.3 モジュール構成

```
src/kakutei_crypto/
  ledger.py       Entry（dataclass）、台帳 CSV の読み書き
  parsers/
    __init__.py   ヘッダーで形式を判定して振り分け
    okj.py        OKJ 注文履歴・入出金口座履歴
    coincheck.py  Coincheck 様式1
  check.py        整合性チェック（時価の欠落、数量がマイナス、未分類）
  engine.py       総平均法・移動平均法 → 年×銘柄の結果
  report.py       端末表示 + xlsx 出力
  cli.py          kakutei import / check / calc
plugin/           Claude Code プラグイン（/crypto-tax スキル）

examples/         合成データ（架空ユーザー）とその期待結果
```

### 4.4 パーサー仕様（実ファイルの形式から）

**OKJ 注文履歴**（`注文id,注文日時,注文銘柄,注文種別,売買,…,約定数量,平均約定価格,注文代金,約定代金,ステータス`）
- 数値は前後の空白と桁区切りカンマを除去する。
- `約定数量 > 0` の行だけを対象にする。`売買` が 購入 → buy、売却 → sell。jpy_value = 約定代金。
- 手数料列がないため、fee は空にして `note` に「注文履歴には手数料なし。取引口座履歴を推奨」と書く。

**OKJ 入出金口座履歴**（`入出金id,日時,資産,入出金内容,数量,残高,手数料`）
- `資産 = JPY` の行はスキップする。
- 数量 < 0 → transfer_out、数量 > 0 → transfer_in。手数料（負の数）は同じ資産の fee として記録する（数量とは別に差し引かれるものとして扱う）。
- 入出金内容が「出金・出庫」「入金・入庫」以外なら、kind は数量の符号で決めたうえで `note` に「要確認: <内容>」と書く（報酬の可能性）。

**Coincheck 様式1**（`取引日時,取引種別,取引形態,通貨ペア,増加通貨名,増加数量,減少通貨名,減少数量,約定代金,約定価格,手数料通貨,手数料数量,…`）
- 取引日時が空の行（残高セクション）は読み飛ばす。
- 増減の組み合わせで kind を決める：JPY 減・暗号資産増 → buy、暗号資産減・JPY 増 → sell、暗号資産 2 種 → swap、増のみ → transfer_in（取引種別に「報酬」「受取」「配布」「ステーキング」「貸」を含めば reward）、減のみ → transfer_out。
- jpy_value は、相手側が JPY ならその数量、それ以外は約定代金。

### 4.5 チェック（`kakutei check`）

エラー（計算を止める）:
- swap / reward で jpy_value が空
- 全交換業者の合算で、ある時点の保有数量がマイナスになる（取込み漏れか、opening が必要）

警告:
- note に「要確認」がある行
- 手数料情報がないファイル由来の行

### 4.6 出力

- 端末：年ごと・銘柄ごとの A〜I と、収入金額・必要経費・所得金額。
- xlsx：`計算書_<年>` シート（国税庁「暗号資産の計算書」の 4・5 欄に準じた形）と、`明細` シート（全 Entry と、それぞれの取得・譲渡・原価への影響）。

## 5. Claude Code プラグイン（`/crypto-tax`）

SKILL.md で Claude に次の手順を指示する:
1. 指定フォルダのファイルを列挙する。既知形式は `kakutei import` に渡す。
2. 未知の CSV や PDF（例: bitFlyer の月次報告書）は Claude が読み、統一台帳の行を作る。各行の `source` に出典を書き、推測した値は `note` に「推定」と明記する。追加する行はユーザーに見せて確認を取る。
3. `kakutei check` のエラーを解消する。時価が欠けている場合はユーザーに値を尋ねるか、交換業者の公開価格を調べて出典を note に書く。**数値をでっち上げない**。
4. `kakutei calc` を実行し、結果と注意点（対象外の取引など）を説明する。
5. Claude は所得金額を自分で計算しない。

## 6. テスト

- エンジン：国税庁 FAQ 1-1、1-3、1-5、2-4（両方の方法）、2-8 をそのままテストケースにする。加えて報酬、分裂、暗号資産手数料、年をまたぐ繰越。
- パーサー：実ファイルの形式を模した**合成**の固定データ（実データはリポジトリに入れない）。
- check：時価の欠落と数量マイナスを検出できること。
- CLI：examples/ を import → calc して、期待値と一致すること。
